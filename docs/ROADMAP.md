## 1. プロジェクトの方向性

「わるん会計」は、小規模な個人経営の飲食店を主対象とするAndroidアプリです。単なる帳簿入力にとどまらず、店主が**5秒で現在の経営状態を把握できる経営支援アプリ**を目指します。

入力負担は、端末内OCR、候補抽出、入力保持、安全な自動化によって減らします。一方で、OCR結果や計算による推定値を無確認で確定せず、根拠と不確実性を示したうえで、経営判断に使える数字を分かりやすく提示します。

開発では、次を優先します。

1. 入力途中のデータと証憑を失わない。
2. 支出や売上を重複保存・重複集計しない。
3. 推定値、参考値、ユーザー確認済みの値、Room保存済みの値を区別する。
4. 既存データをMigrationで安全に引き継ぐ。
5. 将来のレシート、領収書、通帳、請求書、その他資料を共通管理できる余地を残す。

## 3. 現在地

### 3.1 OCRから支出個別保存まで

現在の支出OCRフローは次のとおりです。

```text
CameraX撮影
  → pending JPEGとReceiptCaptureResult
  → ML Kit日本語OCR（rawText）
  → ReceiptParser（店舗名・購入日時・合計金額の候補）
  → 編集可能なOCRレビュー
  → 支払先・支出日・金額をExpenseInputへ反映
  → ユーザーが支出フォームの「保存」でExpenseRecordを個別保存
  → pending JPEGを正式Evidenceへ昇格
  → ExpenseEvidenceLinkRecordで永続関連付け
```

このフローでは、OCR候補の確認、ExpenseRecord保存、画像正式化、永続リンクまで実装済みです。OCR候補は支出入力へ反映するだけでは保存されず、ユーザーの保存操作が必要です。

### 3.2 画像・関連付け・再起動時の扱い

| 確認事項 | 現在の状態 |
| --- | --- |
| pending画像は正式証憑として保存済みか | **いいえ**。アプリ内部の`receipt-images/pending`にある一時ファイル。 |
| ExpenseRecordとの正式な証憑関連付けがあるか | **はい**。保存時に`EvidenceRecord`と`ExpenseEvidenceLinkRecord`をTransaction保存する。`receiptId`は変更しない。 |
| OCRフローからReceiptRecordが保存されるか | **いいえ**。通常のReceiptRecord保存経路は別に存在するが、OCRレビューからは呼ばれない。 |
| 支出個別保存時に画像が正式領域へ移るか | **はい**。DB保存後にSHA-256を検証してstored領域へ正式化し、途中失敗はジャーナルから再試行する。 |
| 再起動後の証憑保持が保証されるか | **はい**。storedファイルとRoomの永続リンクから再読込する。ファイルなし・サイズまたはSHA-256不一致時は表示しない。 |
| OCR rawTextや候補は正式保存されるか | **いいえ**。画面状態として保持されるが、Roomの会計データまたは正式証憑ではない。 |

### Phase 4A 正式証憑保存

**状態: 実装済み。**

目的は、pending画像を一時ファイルのまま放置せず、保存成功を確認でき、アプリ再生成・再起動後にも読み戻せる正式領域へ安全に昇格させることです。

実装済みスコープ:

- pending画像から正式保存領域への、失敗安全なcopyまたはmove。
- 書き込み完了、0バイトでないこと、読み戻し可能であることを確認してからpendingを処理する。
- 同じ入力に対する再試行を冪等にし、二重保存を防ぐ。
- 安定した識別子から正式ファイル参照を再構築できるようにする。
- Activity再生成、プロセス再生成、アプリ再起動後の再読込を確認する。
- 正式化失敗時は元のpending画像と支出入力を保持する。
- 正式画像の生成、再読込、重複防止、失敗rollback、0バイト拒否を自動テストする。

設計上の注意:

- レシート専用の保存モデルへ固定しない。
- 正式保存の識別子、メタデータ、ファイル配置、暗号化、保持期限はこの文書では確定しない。
- Room変更が必要になった時点で、schema、Migration、既存データへの影響を提示してユーザー確認を得る。
- OCR rawTextやParser候補を、画像の正式化だけを理由に確定会計値へ昇格させない。

## 6. 各Phaseの完了条件

### 6.1 共通の完了条件

実装Phaseを完了と判断するには、少なくとも次を満たします。

- 受入条件と実際に確認した結果が一致する。
- 意図したPhase以外のコード、Room、Migration、保存、集計に差分がない。
- `git diff --check`が成功する。
- `.\gradlew.bat testDebugUnitTest`が成功する。
- `.\gradlew.bat assembleDebug`が成功する。
- `.\gradlew.bat compileDebugAndroidTestKotlin`が成功する。
- 追加・変更したAndroid依存部分に必要なinstrumented testまたは実機確認を行う。
- 失敗、skip、未実行、実機未確認を成功と分けて報告する。
- ユーザーがPhaseの確定を承認した後に限りcommit・pushし、`git status -sb`でremote同期済みかつworking tree cleanを確認する。

### 6.2 Phase 4A

- 保存後の正式画像を安定した識別子から再読込できる。
- Activity再生成、プロセス再生成、アプリ再起動後にも参照できる。
- 0バイト、破損、書き込み途中のファイルを正式保存成功にしない。
- 同一要求の再試行で二重ファイルを作らない。
- 正式化成功後だけ、合意した条件でpending画像を処理する。
- 失敗時はpending画像と支出入力を保持し、再試行できる。
- 生成、再読込、失敗rollback、重複防止、削除条件の自動テストが成功する。

### 6.3 Phase 4B

- ExpenseRecordから関連Evidenceを取得でき、未関連Evidenceを誤表示しない。
- 保存済みレシートの有無、画像表示、拡大、再起動後の再読込を確認できる。
- 同一Evidenceを別支出へ関連付けず、同一保存の再試行を冪等に処理する。
- 削除・差し替え・複数画像追加UIは未実装範囲として明示する。
- Room変更を伴う場合、Database version、新Migration、新schema JSON、開始version別のMigrationテストが揃う。
- 既存Roomデータと既存ReceiptRecord保存経路に回帰がない。

### 6.4 Phase 5

- 指標ごとに式、期間、入力データ、推定／確定区分を文書化する。
- 計算はUI非依存の純粋Kotlinとしてテストできる。
- 日次・月次、0件、0除算、欠損、未入力、月境界を安全に扱う。
- 仕入日ベース原価率と棚卸反映後原価を誤表示しない。
- legacy値とExpenseRecordを二重計上しない。
- 現在の売上・支出・現金・客単価の回帰テストが成功する。

### 6.5 Phase 6

- 今日／今月を切り替え、主要指標を短時間で判読できる。
- 推定値、参考値、確定値が視覚・文言の両方で区別できる。
- 各数値から算出根拠と不足データを確認できる。
- 目標がある場合、残額と対象期間を正しく表示する。
- 閾値未確定の指標を独断で色分けしない。
- スマホ・タブレット、縦横、スクロール、文字拡大で主要操作へ到達できる。

### 6.6 Phase 7

- 指定月の会計データと証憑を、承認済み形式で出力できる。
- 出力前検証で未確認・欠損・証憑不足を表示する。
- CSV、ZIP等の生成物を再度開いて内容を検証できる。
- 件数、期間、金額合計、証憑対応がアプリ内データと一致する。
- 再出力でデータや証憑を重複保存・削除しない。
- 個人情報と実データをログやGitへ含めない。

### 6.7 Phase 8

- クラウド障害や未接続でもローカル入力・保存を継続できる。
- バックアップ対象、世代、暗号化、認証、復元手順が明確である。
- 同一データの再送、競合、途中失敗を安全に処理する。
- 新端末または初期状態から、承認済み手順で復元を確認できる。
- 特定サービス実装をGatewayの外へ漏らさない。
- 紙運用とバックアップ未完了時のユーザー案内を確認する。
